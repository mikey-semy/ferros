# Journal — M6: Storage + filesystem

> Диск выбран **virtio-blk** (а не ATA/AHCI) — современный, быстрый, чисто эмулируемый
> QEMU интерфейс из того же семейства, что и будущий virtio-net (M8). virtio — это
> PCI-устройство, поэтому первый шаг — **перечисление шины PCI**. Файловую систему читаем
> **своим кодом (FAT)** — как hand-rolled ELF-загрузчик (D9/D10): без зависимостей, полный
> контроль, teach-as-we-go. Разбивка: M6a PCI → M6b virtio-blk (чтение секторов) → M6c
> FAT-чтение → M6d VFS + файловые сисколлы. См. `docs/DECISIONS.md` D11.

## 2026-06-27 — M6a: перечисление шины PCI

Чтобы найти диск virtio-blk, ядру сперва нужно **увидеть, что висит на шине PCI**. M6a —
это фундамент: читаем конфигурационное пространство устройств и составляем их список.

- **Что такое PCI.** Шина, к которой подключены устройства; у каждого есть 256-байтная
  «анкета» — *конфигурационное пространство*: производитель, идентификатор, класс и адреса
  его регистров (BAR'ы). На x86 «механизм #1» читает её через два 32-битных порта:
  `0xCF8` (адрес: шина/слот/функция/смещение) и `0xCFC` (данные). Пишем координаты в один,
  читаем слово из другого.
- **`arch/x86_64/pci.rs`** (шов, CONVENTIONS §1): только механика портов —
  `config_read_u32` / `config_write_u32`. Пара «адрес→данные» обёрнута в `without_interrupts`,
  чтобы между ними никто не переписал 0xCF8 (атомарность). Весь сырой `unsafe` — здесь
  (D9). `config_write_u32` пока не используется — он понадобится в M6b (bus-master,
  настройка очереди virtio).
- **`drivers/pci.rs`** (переносимая часть): модель `PciDevice` (координаты + анкета + сырые
  BAR'ы), разбор `Bar` (I/O- против MMIO-, с учётом 64-битных BAR'ов через следующий),
  `enumerate()` (полный перебор 256 шин × 32 слота; функции 1..8 — только если устройство
  многофункциональное, бит `0x80` в header type), `find(vendor, device)` и `init()` —
  печать списка в serial. Портов здесь нет: шину обходим через арх-шов `arch::pci`.
- **Арх-нейтральный псевдоним.** В `arch/mod.rs` добавлен `pub use self::x86_64::pci;` (как
  для `context`/`USER_SPACE_END`), чтобы переносимый драйвер звал `crate::arch::pci`, не
  зная конкретной архитектуры.
- **Диск в QEMU.** В `Cargo.toml` (`test-args` + новый `run-args`) добавлен второй диск
  через контроллер virtio-blk: `-drive if=none,id=disk0,…` + `-device virtio-blk-pci`
  (отдельно от загрузочного диска, который bootimage даёт первым). Сам образ создаёт
  `build.rs`: raw `target/ferros-disk.img` 4 МиБ с сигнатурой `FERROSM6` в секторе 0
  (M6b прочитает и сверит). Подтверждено: bootimage 0.10.4 знает ключ `run-args`.
- **Тонкость с QEMU.** «Переходное» (transitional) устройство `virtio-blk-pci` по умолчанию
  отвечает на legacy-идентификатор `1af4:1001` и отдаёт legacy-регистры в **I/O-BAR0** —
  именно то, что нужно legacy-драйверу M6b (никакой `disable-modern` не понадобился).
- **Проверка.** `cargo test` — 16 тестов в QEMU зелёные (новый `pci_enumeration`: найден
  хост-мост `8086:1237`, найден virtio-blk `1af4:1001`, его BAR0 — непустой I/O-BAR);
  fmt/clippy чисто. Загрузка headless печатает 7 устройств на шине (хост-мост, ISA/IDE
  PIIX3 как многофункциональное `00:01.x`, ACPI, VGA, e1000, и `00:04.0 1af4:1001` —
  диск), паник нет.

## 2026-06-27 — M6b: драйвер virtio-blk (чтение секторов)

Ядро **прочитало данные с диска** — впервые байты пришли не из образа ядра, а с
(виртуального) устройства хранения. Это и есть смысл M6b: научиться разговаривать с диском
virtio-blk по DMA.

- **Что такое virtio и virtqueue.** virtio — стандарт «паравиртуальных» устройств: гость и
  гипервизор общаются через общую структуру в памяти — **virtqueue** — а устройство
  выполняет запросы по DMA (читает/пишет память гостя напрямую). Быстрее эмуляции ATA/AHCI
  и проще. virtqueue состоит из трёх частей: таблица **дескрипторов** (указатели на буферы),
  кольцо **avail** (гость кладёт сюда головы цепочек-запросов) и кольцо **used** (устройство
  отмечает выполненные).
- **Физически непрерывная память (новое в каркасе).** Legacy-virtio адресует всю очередь
  одним числом — PFN (`phys >> 12`), значит она обязана лежать в непрерывной физической
  памяти. Куча для этого не годится (виртуально непрерывна, физически разбросана). Добавлен
  `BootInfoFrameAllocator::allocate_contiguous(count)` — ищет серию подряд идущих фреймов.
- **`arch/x86_64/io.rs`** (новый шов): порты ввода-вывода с **динамическим** номером
  (`inb/outb/inw/outw/inl/outl`). У legacy-virtio регистры — в портах по базе из BAR0,
  известной лишь в рантайме; держим работу с портами в `arch` (CONVENTIONS §1), а не в
  драйвере. Арх-нейтральный псевдоним — `crate::arch::io`.
- **`drivers/virtio_blk.rs`**: инициализация (включить I/O-пространство + bus-mastering в
  регистре команд PCI → сброс → ACK/DRIVER → фичи=0 → выбрать очередь 0, узнать её размер,
  выделить непрерывную virtqueue, отдать устройству её PFN → DRIVER_OK), плюс
  `read_sector(lba, &mut [u8; 512])`. Запрос на чтение — цепочка из 3 дескрипторов:
  заголовок-команда (`type=IN, sector=lba`, устройство читает) → буфер данных (устройство
  пишет) → байт статуса (устройство пишет). Кладём голову в avail, **барьер памяти**
  (`fence`) перед сдвигом `avail.idx` (чтобы устройство не увидело недописанную цепочку),
  пишем в Queue Notify, опрашиваем `used.idx`. Просим устройство НЕ слать прерывания
  (`VIRTQ_AVAIL_F_NO_INTERRUPT`) — мы опрашиваем, IRQ virtio пока не обрабатываем. Весь
  сырой доступ к кольцам — volatile по `phys + phys_mem_offset`, `unsafe` собран в методах
  с `// SAFETY` (D9).
- **Спецификация сверена** (а не «придумана»): смещения регистров, раскладка virtqueue
  (align 4096, PFN), формат запроса virtio-blk и последовательность инициализации — по
  спецификации OASIS virtio (legacy) и эталонному драйверу Linux.
- **Проверка.** `cargo test` — 18 тестов зелёные (новый `virtio_blk_read`: устройство
  поднялось `queue_size=256, capacity=8192 секторов`; сектор 0 прочитан, сигнатура
  `FERROSM6` совпала); fmt/clippy чисто. Загрузка headless печатает
  `sector 0 starts with: [70, 69, 82, 82, 79, 83, 77, 54]` (= ASCII «FERROSM6»), паник нет.

## 2026-06-27 — M6c: чтение FAT32

Ядро **прочитало файл по имени** — `HELLO.TXT` с диска, не сектор по номеру. Это первый
файловый слой: поверх блочного устройства появилось понятие «файл в каталоге».

- **Что такое FAT.** Диск разбит на **кластеры**; отдельная таблица (FAT) для каждого
  кластера хранит номер *следующего* — файл это цепочка кластеров (односвязный список через
  FAT). Каталог — особый файл из 32-байтных записей (имя 8.3, атрибуты, первый кластер,
  размер). Раскладка тома FAT32: `[ зарезервированные | FAT×N | данные (кластеры от №2) ]`;
  параметры — в BPB (сектор 0); корень — цепочка кластеров от `BPB_RootClus`.
- **Развилки (по запросу).** Взяли **FAT32** (как в роадмапе) — пришлось вырастить образ
  диска до 64 МиБ (FAT32 требует ≥65525 кластеров, в 4 МиБ не влезает). Тестовый образ
  создаём крейтом **`fatfs`** как **build-зависимостью** (хост-инструмент в `build.rs`
  форматирует образ и кладёт файл) — в рантайме ядра его нет; ядро читает FAT **своим
  кодом** (как hand-rolled ELF, D9/D10). См. `DECISIONS.md` D11.
- **`build.rs`**: подключён `fatfs` (`default-features=false, features=["std","alloc"]` —
  без chrono). Форматируем 64-МиБ буфер как FAT32 (в fatfs 0.3 с фичей `std` его трейты
  есть у `std::io::Cursor` напрямую — обёртка не нужна), создаём `HELLO.TXT` с известным
  содержимым, пишем образ. Идемпотентно: не пересоздаём, если уже FAT нужного размера.
- **`src/fs/fat.rs`** (новый, переносимый): `Fat32::mount()` разбирает BPB и считает
  `fat_start`/`data_start`/`root_cluster`; `read_file(name)` ищет запись 8.3 в корне
  (пропуская LFN/метку тома/удалённые), берёт первый кластер и размер, идёт по цепочке через
  `next_cluster` (запись FAT32 = 32 бита, маска `0x0FFFFFFF`, EOC ≥ `0x0FFFFFF8`), набирая
  ровно `size` байт. Читает по одному сектору через `virtio_blk::read_sector` (без кэша).
- **Тонкость: образ сменил формат.** Раньше сектор 0 нёс сигнатуру `FERROSM6` (M6b-тест её
  проверял). Теперь сектор 0 — загрузочный сектор FAT, поэтому `virtio_blk_read` сверяет
  сигнатуру загрузсектора `0x55AA` (по-прежнему доказывает, что DMA-чтение вернуло верные
  байты), а разбор самого FAT проверяет новый тест `fat_read`.
- **Проверка.** `cargo test` — 19 тестов в QEMU зелёные (`fat_read::reads_hello_txt` —
  содержимое совпало; virtio/PCI — по-прежнему). fmt/clippy чисто. Загрузка headless печатает
  `[fat] HELLO.TXT (30 bytes): "ferros M6c: hello from FAT32!\n"`, паник нет.

## 2026-06-27 — M6d1: отказоустойчивый доступ к памяти пользователя

M6d разбит надвое. Сначала — **консолидация**: закрываем дыру, из-за которой кривой
пользовательский указатель в системном вызове ронял **всё ядро**. Это триггер из плана
наращивания серьёзности (в M6d2 у `read` появятся пользовательские буферы — самое время).

- **Проблема.** `with_user_bytes` проверял только, что указатель в пользовательской половине
  (не адрес ядра), но не что он **отображён**. Валидный по диапазону, но неотображённый
  указатель (`write(1, 0xDEAD…, n)`) → ядро в кольце 0 читает его → page fault из кольца 0 →
  паника. Пользователь мог уронить ядро одним сисколлом.
- **Решение (предпроверка, а не extable).** Перед доступом обходим **активные таблицы
  страниц** и проверяем, что каждая страница диапазона present и помечена `USER_ACCESSIBLE`
  (`mm::paging::user_range_accessible`). Если нет — возвращаем `-EFAULT`, не трогая память.
  Корректно на одном ядре: syscall идёт с `IF=0`, поэтому между проверкой и доступом
  отображение под нами не меняется. Это проще «настоящего» Linux-механизма fault-fixup
  (extable): тот однопроходный и переживает гонки на SMP, но требует asm-копирования с
  метками и поиска RIP в `#PF` — оставили на будущее (HARDENING).
- **`mm/paging.rs`**: оффсет физпамяти сохраняется глобально в `init` (раньше только
  возвращался), плюс `user_range_accessible(start, len, need_write)` — строит `OffsetPageTable`
  над активной таблицей (из CR3) и проверяет флаги листовых записей. `map_to` ставит
  `USER_ACCESSIBLE` и на промежуточные таблицы, так что флаг листа — верный признак
  «пользовательская страница».
- **`syscall/uaccess.rs`**: `with_user_bytes` теперь после проверки границ зовёт
  `user_range_accessible` и отдаёт `-EFAULT`, если диапазон не отображён как пользовательский.
- **Тест `tests/uaccess_fault.rs`** (со стороны ядра, без процесса): три «плохих» указателя →
  `EFAULT` (неотображённый пользовательский `USER_STACK_VA`; адрес ядра; **куча ядра** —
  отображена в пользовательской половине, но без `USER_ACCESSIBLE`), и один валидный
  (вручную отображённая USER-страница) — читается, возвращает записанные байты. Случай с
  кучей доказывает, что смотрим именно на флаг пользователя, а не только на «отображено».
- **Проверка.** `cargo test` — 22 теста в QEMU зелёные (новый `uaccess_fault`; `userspace_*`
  по-прежнему — значит валидные пользовательские буферы `write` всё ещё принимаются);
  fmt/clippy чисто; загрузка headless без паник.
